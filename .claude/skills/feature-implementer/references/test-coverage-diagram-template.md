# Test Coverage Diagram Template

> **Purpose**: TDD実装段階で変更コードのすべての分岐/エラー/ユーザーフローを体系的にマッピングし、テストギャップを事前に識別する
> **When**: feature-implementerのStep 3（TDD実装）開始前に実行

## Iron Rule

```
テストギャップがあるコードをコミットしない。
NO COMMITS WITH UNTESTED CODE PATHS.
```

---

## Step 1: コードパス追跡（Code Path Tracing）

実装するコードのすべての実行経路をマッピングする。diffのハンクだけでなく**ファイル全体**を読んでコンテキストを把握する。

各変更ファイルについて:

1. **エントリーポイント識別**: ルートハンドラー、エクスポート関数、イベントリスナー、コンポーネントレンダー
2. **データフロー追跡**:
   - 入力元: リクエストパラメータ、props、DB、API呼び出し
   - 変換: 検証、マッピング、演算
   - 出力: DB書き込み、APIレスポンス、レンダリング、副作用
   - 各段階の失敗可能性: null/undefined、無効な入力、ネットワークエラー、空のコレクション
3. **分岐ダイアグラム作成**:
   - 追加/修正されたすべての関数/メソッド
   - すべての条件分岐（if/else、switch、三項演算子、guard clause、early return）
   - すべてのエラー経路（try/catch、error boundary、fallback）
   - 他の関数呼び出し（該当関数の未テスト分岐も追跡）
   - エッジケース: null入力、空配列、無効な型

---

## Step 2: ユーザーフロー + インタラクション + エラー状態マッピング

コードカバレッジだけでは不十分である。実際のユーザーインタラクションをカバーする必要がある。

各変更機能について:

- **ユーザーフロー**: このコードに触れるユーザーアクションのシーケンス（例: 「決済クリック → フォーム検証 → API呼び出し → 成功/失敗画面」）
- **インタラクションのエッジケース**:
  - ダブルクリック / 素早い再送信
  - 作業中の離脱（戻る、タブを閉じる）
  - 古いデータでの送信（30分放置、セッション期限切れ）
  - 遅い接続（APIに10秒かかる — ユーザーが見るものは?）
  - 同時アクション（2つのタブ、同じフォーム）
- **エラー状態**:
  - 明確なエラーメッセージ vs 無反応な失敗
  - ユーザーの復旧可能性（再試行、戻る、入力修正）
  - ネットワークなし、API 500、サーバーの無効なデータ
- **境界状態**: 結果0件、結果10,000件、単一文字、最大長

---

## Step 3: 既存テストとの照合（Coverage Check）

ダイアグラムの各分岐を既存テストと照合する。

### 品質スコアリング

| Score | 意味 | 基準 |
|:-----:|------|------|
| ★★★ | 完全 | 動作 + エッジケース + エラー経路テスト |
| ★★ | 基本 | Happy pathのみテスト |
| ★ | 最小 | Smoke test / 存在確認 / 単純なassertion |

### テストタイプ決定マトリクス

| 条件 | 推奨タイプ | ダイアグラムマーキング |
|------|----------|:----------:|
| 3+コンポーネント/サービスにまたがるユーザーフロー | E2E | `[→E2E]` |
| モッキングが実際の失敗を隠す統合ポイント | E2E | `[→E2E]` |
| 認証/決済/データ破壊フロー | E2E | `[→E2E]` |
| LLM呼び出し品質検証 | Eval | `[→EVAL]` |
| 純粋関数、内部ヘルパー | Unit | (デフォルト) |
| 単一関数のエッジケース | Unit | (デフォルト) |

### Regression Iron Rule

```
IRON RULE: 既存動作を変更するdiffで既存テストが該当経路をカバーしていない場合、
回帰テストを即座に作成する。AskUserQuestionなしで。スキップなしで。
```

回帰判定基準:
- diffが既存動作を修正（新規コードではなく）
- 既存テストスイートが変更経路をカバーしていない
- 変更が既存呼び出し元に新しい失敗モードを導入

---

## Step 5: ギャップテスト生成

ギャップが識別されたら:

- **AUTO**: 純粋関数の単体テスト、既存テスト関数のエッジケース → 即座に作成
- **ASK**: E2Eテスト、新しいテストインフラが必要、曖昧な動作 → ユーザー確認後に作成
- **[→E2E]** マーキング経路: 常にASK
- **[→EVAL]** マーキング経路: 常にASK
