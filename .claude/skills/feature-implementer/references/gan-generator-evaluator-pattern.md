# GAN Generator-Evaluator分離パターン

> Source: ECC gan-style-harness/SKILL.md + agents/gan-evaluator.md (Anthropic Harness Design Paper, March 2026)
> Transplant: tp-everything-claude-code-round2-20260402, asset-R2-02 (inspired)

## 目的

> "エージェントに自分の作業を評価させると、病的な楽観主義者になる — 平凡な出力を褒め、正当な問題を合理化する。
> しかし、**別の評価者**を冷徹に厳格になるようエンジニアリングすることは、生成者に自己批判を教えることよりもはるかに扱いやすい。"
>
> — Anthropic Harness Design Paper (2026-03-24)

これがGAN（Generative Adversarial Networks）の核心的な動力学である。Generatorは生産し、Evaluatorは批判し、そのフィードバックが次の反復を導く。

## 核心原則

### 1. 生成と評価の分離

生成者（コード作成）と評価者（品質検証）は**別の役割/エージェント**でなければならない。
同じエージェントが両方の役割を担うと、自己バイアスが不可避になる。

### 2. 冷徹な評価者の設計

評価者の自然な傾向は寛容さである。これを積極的に矯正する必要がある。

**必ず行うこと:**
- あらゆる欠陥、あらゆる手抜き、あらゆる平凡さの兆候を探す
- AI-スロップ美学（ジェネリックなグラデーション、ストックレイアウト、ありきたりなパターン）を強く減点する
- エッジケースをテストする（空の入力、非常に長いテキスト、特殊文字、素早い連続クリック）
- プロの人間開発者がリリースできる水準と比較する

**絶対にしないこと:**
- 「全体的に良い努力」または「堅実な基盤」— こうした表現は回避である
- 発見した問題を自分で合理化しない（「些細だ、おそらく問題ない」→禁止）
- 努力や「潜在力」に点数を与えない
- 合格点は**AIにしては良い**ではなく**本当に良い**ことを意味しなければならない

### 3. AI-スロップ防止ルーブリック

| 基準 | 重み | 採点体系 |
|------|--------|-----------|
| デザイン品質 | 0.3 | 視覚的階層、間隔、タイポグラフィ、色の調和 |
| 独創性 | 0.2 | ジェネリックなAI出力ではなく意図的なデザイン決定 |
| 職人技 | 0.3 | ディテールの水準、一貫性、エッジケース処理 |
| 機能性 | 0.2 | すべての機能の動作可否、エラー処理 |

### 点数較正基準

| 点数 | 意味 |
|------|------|
| 1-3 | 壊れている — 基本機能が未達 |
| 4-5 | AIが生成した水準 — 動作するがありきたり |
| 6 | 悪くないがジェネリック — 「AIが作ったっぽい」 |
| 7 | ジュニア水準として堅実 |
| 8 | エキスパート水準 — リリース可能 |
| 9 | シニア水準 — 洗練されている |
| 10 | リリース準備完了 — プロが誇れる水準 |

## GANパターン vs 標準レビュー比較

| 状況 | 使用パターン |
|------|-----------|
| 完全なアプリのビルド（一文プロンプト → プロダクション） | **GANパターン** |
| 高い視覚品質が必要なフロントエンド | **GANパターン** |
| 「AIスロップ」美学が許容できないプロジェクト | **GANパターン** |
| 単一ファイル修正、迅速なバグ修正 | 標準レビュー |
| 予算制約（<$10） | 標準レビュー |
| テストが明確に定義されたTDD作業 | TDDワークフロー |

## brief2dev適用ガイド

### SDD 2-stageレビューとの統合

feature-implementerのSDDモードは既に2-stageレビューを実行している:
1. `sdd-spec-reviewer-prompt.md` — スペック準拠検証
2. `sdd-quality-reviewer-prompt.md` — コード品質検証

GANパターンはこの2-stageを**強化**する:
- Quality reviewerに「冷徹な評価者」原則を注入
- AI-スロップ減点基準の適用
- 点数未達時に実装者へフィードバック → 修正サイクル

### 適用タイミング

1. **feature-implementer Step 4（レビュー段階）**: Quality reviewerが冷徹な評価者として動作
2. **score < threshold**: 問題を実装者にフィードバック → 修正後に再レビュー
3. **収束時**: 最終Go判定

### 「病的な楽観主義者」検知パターン

レビューで以下の表現が出た場合、評価が十分に厳格でない兆候:
- 「全体的に良い実装」→ 具体的な問題を探せ
- 「些細な改善点」→ 些細ではない、基準に合っているか?
- 「将来改善可能」→ 今修正すべきではないか?
- 「努力が見える」→ 努力は点数ではない
